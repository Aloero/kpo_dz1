# ВышКат

Проект "ВышКат" - консольное приложение на Go для учёта парка. Приём техники через техосмотр, отчёты, инвентаризация.

## Запуск

```bash
go run .
```

Меню: 1. добавить транспорт, 2. добавить вещь, 3. отчёт, 4. транспорт для новичков, 5. инвентаризация, 0. выход. Энергия вводится с точкой или запятой. Пустое поле, кривой номер или дубликат номера дают сообщение и повторный ввод, конец ввода завершает программу.

Чтобы демо воспроизводилось одинаково, я записал ответы в demo.txt:

```bash
go run . < demo.txt
```

Лента показывает пустые отчёты, приёмку исправного самоката и велосипеда, отказ неисправному самокату S-2, шлем и зарядную станцию, повторный номер S-1 и итоговые отчёты.

Прогон: 2 транспорта и 2 вещи, 3,75 кВт·ч в сутки. В список новичков попадает только самокат S-1 (простота 6), велосипед B-1 (5) не попадает, отклонённого S-2 на балансе нет.

Собрать:

```bash
go build .
```

## Проектирование

Доменная часть в пакете fleet. Я сначала нарисовал, написал на бумаге, какие свойства есть у каждого объекта, подумав, сделал интерфейсы:

- InventoryItem (название + инвентарный номер)
- EnergyConsumer (суточный расход) только у самоката и зарядной станции
- Transport расширяет InventoryItem и добавляет простоту для новичка (1,10) и признак исправности.

Общие поля вынес в приватные структуры asset и vehicle, конкретные типы их включают. Нету наследования, велосипеду нечего брать у шлема.

Fleet в fleet.go ведёт один баланс. Номера уникальны, пробелы обрезаются, сравнение без учёта регистра. Суммарная энергия считается через type assertion на EnergyConsumer, поэтому новое устройство с расходом автоматически попадёт в отчёт. Inventory() отдаёт копию среза, чтобы консоль не задирала внутреннее состояние.

ServiceCenter принимает исправный транспорт и отклоняет неисправный. Признак исправности вводит оператор после осмотра. Отклонённая техника не встаёт на баланс и не занимает номер.

## Вопросы

1. Наиболее явно применён DIP, Fleet знает только интерфейс Inspector и получает его через конструктор fleet.go. В тесте я подменяю техосмотр стабом, решение о приёмке меняется.
2. Сознательно ограничен OCP в консоли. Fleet расширяется без правок, а под новый вид транспорта в console.go придётся добавить пункт меню и ветку в addTransport.
3. Что сломается при расширении:
 - электровелосипед включает Bicycle и реализует EnergyConsumer. Дописываю пункт в меню консоли. Что всё это принимается, проверяет TestNewTransportType.
 - сотрудник по преамбуле на баланс не ставится, поэтому InventoryItem ему не нужен. AddTransport/AddThing его не примут.
 - склад запчастей, новая структура поверх asset в fleet. Баланс уже принимает любой InventoryItem, склад вынесу отдельным сервисом, техосмотр транспорта не трогаю.
4. Решение техосмотра фиксируют TestRunUsesInjectedInspection (стаб подставлен в тот же контейнер, из которого собирается приложение) и TestRejectedTransportDoesNotChangeFleet (отказ не меняет баланс). Границу 5/6 для новичков фиксирует TestBeginnerBoundary. Подмена зависимости, провайдер inspector в main.go в prod отдаёт ServiceCenter, в тесте стаб. Fleet получает зарегистрированный экземпляр и ни про что не знает.

Остальные принципы:

SRP: консоль только ввод/вывод, Fleet баланс и выборки, ServiceCenter решение о допуске.
OCP: Fleet через интерфейсы, новый вид транспорта не меняет приёмку, энергию и отбор новичков.
LSP: Scooter, Bicycle и тестовый electricBicycle работают по общему контракту.
ISP: инвентаризация, энергия и осмотр разделены на интерфейсы, велосипед и шлем не тянут за собой EnergyConsumer.

## DI-контейнер

container.go, 30 строк: карта провайдеров и карта созданных экземпляров. Первый resolve вызывает провайдер и запоминает результат, то есть сервисы синглитоны. Места, где я застрял: провайдер должен уметь запросить зависимость у самого контейнера, и я не понимал, как это аккуратно оформить. Поэтому провайдеры принимают на вход сам контейнер.

Регистрация в run в main.go: техосмотр вешаю готовым объектом, Fleet и консоль создаю конструкторами, зависимости приходят из контейнера.

## Тесты

```bash
go test -count=1 ./... -coverprofile=coverage.out
go tool cover -func=coverage.out
```

В fleet/fleet_test.go: баланс не меняется при отказе, отчёты считают количество и энергию, граница 5/6, дубликаты номеров и обход техосмотра через AddThing отклоняются, новый вид транспорта принимается без правок.

В console_test.go: TestRunUsesInjectedInspection прогоняет то же приложение со стабом техосмотра в том же контейнере, стаб принимает неисправный самокат и отклоняет исправный, я проверяю, что он вызван ровно один раз на тот объект, что подали. TestContainerReusesInstance проверяет, что контейнер создаёт сервис один раз.

Проверено на Go 1.27.2, сборка, `go vet ./...`.

## Роль ИИ

ИИ использовал в трёх местах. ИИ ассистент (редко обращался): Модель, Fleet, консоль (кроме readEnergy), тесты пакета fleet.

1. DI-контейнер: container.go и регистрация провайдеров в main.go. Я не мог сообразить, как провайдеру запросить зависимость у самого контейнера, и попросил ИИ показать минимальный контейнер с ленивым созданием и кэшем экземпляров. Набросок переписал, свои имена методов register/resolve.
2. readEnergy в console.go: как принимать и запятую, и точку, и не впускать NaN/Inf на баланс. ИИ предложил вариант, который ронял команду при первой ошибке, я переделал в цикл с повторным вводом.
3. Первый вариант console_test.go: пример стаба для Inspector и как его подставить в приложение. Поверх наброска добавил второй кейс (отклоняем исправную технику), проверку, что стаб вызван ровно раз, и TestContainerReusesInstance.
